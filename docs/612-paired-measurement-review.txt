PREREQUISITES (must be independently verified, not assumed from green CI)
Build images using the supported Docker build from those exact trees; no old-live
substitution. Preserve immutable local image IDs, baked source/release identity,
Node/Python versions, production configuration, Library snapshot/data hashes and
schema/state-codec compatibility of the shared fixtures. Actual byte inventories
must establish equal assets/configuration/fixture-codec identities and runtime
versions. Document any differing field and stop rather than silently normalize it.
The local Docker daemon is available but has no images cached at preparation.

--preflight requires a reviewed external inventory receipt with status=verified,
reviewer and evidence_source, plus before/after records containing image_id,
source_sha, assets_sha256, config_sha256, fixture_codec_sha256, node_version and
python_version. The driver checks hashes' shape, image/source association and
field equality before measurement. It does not authenticate an inventory merely
because a JSON file says verified: the independent reviewer must validate its
source evidence. No such preflight receipt exists yet.

COMMON FIXTURES

seed_lyrics_capacity_receipts.mjs and lyrics_capacity_server.mjs --prepare in the

.sha256 file. manifest.json contains an exact relative-path -> SHA256 map under

--fixtures is mandatory. Verify complete membership and every hash before each

paired_fixture_sha256 must match the common receipt. No per-arm random generation.

PRESPECIFIED REPLICATION AND ORDER
Use the four existing shard cell sets, each on one dedicated host. On EACH host,
run two repetitions of ALL three arms sequentially in fresh containers:
  repetition1: before-loaded, after-loaded, after-unloaded
  repetition2: after-unloaded, after-loaded, before-loaded
--candidate-first reverses the first order and correspondingly the second.
Thus each exact workload gets both orders on the SAME host, not different orders
on different populations. Do not run arms concurrently or move repetition2 to a
new host. Retain host, experiment ID, order, image IDs and all failed receipts.
Each arm keeps1CPU/2GiB and1792MiB gates. No store removal, workload truncation,
cache flushing, retry-until-green or qualification substitution. Two repetitions
provide repeated descriptive evidence, not a tail-risk estimate or a confidence
interval. This is108 workload executions total (18cells/modes x3arms x2repetitions),
plus startup/recovery and fixture preparation; review cost before dispatch.

SEARCH AND VERIFICATION
Each loaded startup times q=love&limit=1, requiring a positive result. Recovery
starts a NEW server process and times the pinned long no-match query in
SEARCH_QUERIES, requiring zero results. Both queries are nonempty and exercise
body scanning. The first-request response digest, snapshot ID, total and query
must match across before/after for each repetition. A mismatch fails the driver.
Legacy main can return search before corpus verification ends; record response
first_search_s separately from verified_ready_s. Readiness must be observed
before the unchanged60second deadline. Late-ready responses are refused, and
request timeouts are capped to remaining time. Implicit health requests retain
the inherited5second default; explicit search/load requests retain their declared
timeout, capped by the same shared deadline. Include verification in the
sampled load window. Candidate-unloaded stays unloaded and has no search timing.

MEDIAN POPULATIONS (do not pool unlike observations)
For each of18 exact workload cells/modes, calculate before minus after-loaded
resident peak in each repetition; take that cell's median of2 paired differences.
Report all18 cell medians and the median of those18 equally weighted values.
Repeat separately for before-loaded versus after-unloaded. Also report raw peak
and margin for every observation and the worst observed cell per arm across both
repetitions. Do not subtract two separately pooled medians.
For latency, report startup representative-query and recovery no-match separately.
Each query has8 paired before/after differences (4hosts x2repetitions). Report
before/after medians and the median of paired differences over those8 pairs, plus
ranges and each pair. Do the same separately for verified_ready_s. Do not pool
representative and no-match timings. Compare assets/configuration, fixture hashes,
source identities and unchanged limits before interpreting any difference.
Host pairing reduces host variation but does not remove filesystem-cache/order
or time drift; two reverse-order repetitions do not establish production savings.

SAMPLING AND CLEANUP
Retain per-cell peak records, sample counts, peak-associated component snapshots,
load-window peak records, image/build hashes, host metadata, order and failures.
The existing sampler does NOT retain every raw sample or continuous maxima;
short transients can be missed. No full raw-sample claim is made.
Every arm has an invocation-owned UUID container name; finally removes it after
completion, timeout or interruption. Cleanup failure stops the experiment and is
recorded. No competing/shared container is removed; no automatic retry.
