# Codex Musica — Exhaustive Repository Audit

**Date:** 2026-08-06 · **Commit audited:** `9720e9d` · **Scope:** the whole repository
**Result:** 205 findings raised, 23 merged as duplicates, 6 refuted, **176 verified** — 1 critical, 17 high, 75 medium, 66 low, 17 nit.

---

## 1. The verdict

This is a genuinely unusual repository, and most of what makes it unusual is good. It is a 157,000-line vanilla-JavaScript system with **zero runtime dependencies**, a catalog of 2,503 traditions and 1,406 instruments, a browser app, a headless engine, a hosted MCP connector, and a static JSON API — and it holds all of that together with a machine-checked promise system, byte-level reproducibility gates, and fault injection that verifies the gates themselves are two-sided. Very few codebases of any size attempt that; almost none written by one person do. The determinism engineering in particular is first-rate: the codepoint-pinned comparator with a documented no-op migration (`scripts/_recipe_stack.js:46-61`), worker merges indexed by catalog position rather than completion order (`scripts/build_static_api.js:116-180`), seeded LCG restarts in the hill-climb (`scripts/search.js:469-473`). The panel's correctness formalist put it exactly right: *"where determinism is engineered it is excellent."* The error messages are better than most commercial products' (`Unknown room: … (search_catalog types=["room"])` tells the caller how to fix itself). Both packages commit lockfiles; CI installs from them; history is squashed so `.git` is 16 MB despite 35 rewrites of a 5.9 MB artifact. Clone cost, dependency reproducibility, and artifact freshness are all solved problems here, and they are solved deliberately.

The failures are therefore not sloppiness — they are **scope failures**, and that is the single most important sentence in this report. Every confirmed defect of consequence is a universally-quantified claim enforced over the subset where it happens to be true. The flagship promise is that the connector returns "the byte-identical string the app shows for the same workspace" (`AGENTS.md:68-70`). It is false the moment anyone edits anything: the app locks prefaces on `prefaceAuto===false` (`src/app.js:12934`), the Node renderer locks on `prefaceLock` (`scripts/_recipe_stack.js:484,488`), and `setVariant` deliberately sets the first and not the second. The gate that covers the promise renders only *un-edited* seeds; the gate that covers editing compares card *state* and never renders. The two gates' input spaces tile neatly around the defect. This same shape recurs at every level: `faults.js` prints "All gates are two-sided" over a strictly smaller set than the gate set (F080); `check_promises` verifies that markers and gates reference each other but never that the gate's scope matches the claim's scope (F058); an in-source comment asserts that `check_app_parity.js` keeps two comparator copies in step, and a direct experiment shows the gate stays green 2503/2503 with one copy regressed (F140, F201). The verification apparatus is large and mostly honest, but its quantifiers are wrong, and wrong quantifiers are worse than no gate — they buy confidence that isn't there.

Beyond that, three concrete things need attention regardless of philosophy. **One critical security defect**: `sync-pages.yml` is a textbook GitHub *pwn request* — it fires on `workflow_run`, checks out the triggering run's `head_sha`, and runs `npm ci` plus build scripts on it while holding a `contents: write` token, and CI runs on fork PRs. An outsider who names their fork branch `main` gets code execution with a write-scoped token against the production branch (F039/F193). **A publicly-exposed, unauthenticated, single-process service with no rate limiting on its main endpoint**: one anonymous POST can block the Render event loop for 19 seconds (F179), another can permanently poison an unbounded module-global cache into OOM (F183), and the tool the connector's own instructions route *every* id lookup through burns 430–960 ms of blocking CPU per call (F045). **And the recipe itself can be silently corrupted**: the prose/rich compressors merge environment chunks into instrument chunks when their labels share a trailing token, so `forró brasileiro` renders "prancing electric baião-2-4-with-zabumba-on-beat-1 bass" today, and under length pressure the electric bass disappears from the output entirely with no elision notice (F001). That is the product's core deliverable being wrong on shipped data, and no gate can see it because both engines share the bug.

## 2. How this audit ran

Seven deep-readers mapped the subsystems (the 18.8k-line app in three slices, the connector, the scripts engine, all ~30 gates plus CI, and the data/docs layer). Ten dimension-specific reviewers — bugs×3, security, performance, architecture, taste, testing, docs/DX, data integrity — produced 110 raw findings. Every finding was then handed to an adversarial verifier instructed to assume it was wrong until the code proved otherwise, with critical/high findings facing two additional independent refuters under majority rule; verifiers ran the repo's own loaders and benchmarked the actual loops rather than reasoning from the source. A six-seat expert panel (minimalist, toolmaker, adversary, performance, formalist, maintainer) then argued through structured rounds — opening arguments, rebuttals, severity court — with findings contested by two or more panelists going to a referee with final authority, two-vote escalations moving severity, and every round's new leads chased by targeted investigators whose findings re-entered verification. That process refuted 6 findings, merged 23 as duplicates, escalated 5 and downgraded 8. Rounds 4–5 (blind-spot hunt, closing arguments) and the automated synthesis pass were cut short by account usage limits; this report is written from the complete round 1–3 transcript and the full verified dossier. Everything below cites `file:line` that a verifier personally opened.

## 3. Critical and high findings

Grouped by defect, because several findings are the same defect seen from different seats.

### C1 · Fork-PR code execution with a write token — `sync-pages.yml` (F039 critical, F193)

`.github/workflows/sync-pages.yml` declares `permissions: contents: write` (`:34-36`) and triggers `on: workflow_run` for the CI workflow (`:28-31`). When a run reports success it checks out `${{ github.event.workflow_run.head_sha }}` (`:53`) — the *triggering run's* commit — and then executes `npm ci` (`:61`) and `node scripts/build_html.js` (`:68`) against that tree. CI itself runs on fork pull requests (`ci.yml:17`). The `branches: [main]` filter on the `workflow_run` trigger matches the run's **`head_branch`**, which for a fork PR is the *attacker's* branch name — so a fork whose branch is named `main` satisfies it. There is no `.npmrc` and no `--ignore-scripts`, so `npm ci` runs lifecycle scripts, and `sharp`/`playwright` already normalize install scripts running.

An outsider with no credentials forks the repo, names the branch `main`, opens a PR whose payload lives in a `postinstall` hook or in a build script (leaving all gate outputs unchanged so CI goes green), and when CI succeeds the publish job executes their code holding a `contents: write` `GITHUB_TOKEN` that `actions/checkout` has already persisted into `.git/config` — before `publish_guard.sh` runs at `:121`. The result is arbitrary push to the production branch that GitHub Pages serves, and since `render.yaml` sets `autoDeploy: true` on `main`, whatever lands there deploys to the live connector.

The panel argued the severity hard. The adversary seat pushed it to critical: *"an outsider with zero credentials gets a write-scoped token, a push to main, and via autoDeploy the live GEMINI key out of the Render process."* The formalist pushed back and was right on one point — `render.yaml:27-28` sets `GEMINI_API_KEY` with `sync: false`, so it lives in Render and never enters Actions; the loot is the GitHub token, not the Gemini key — but conceded F039 is still worst by blast radius because it poisons both what `llms.txt` tells agents to clone-and-run *and* what auto-deploys. Critical stands.

**Fix:** never check out and build `head_sha` in a write-privileged job. Gate on `github.event.workflow_run.event == 'push' && head_repository.full_name == github.repository`, or move publishing into the trusted `push` workflow entirely. Add `--ignore-scripts` to the publish install. Verify the fork/`head_branch` behavior yourself before trusting any filter.

### H1 · The parity cluster: two renderers, two different lock fields (F015, F054, F077, F090)

Four findings, one defect. `setVariant` sets `card.prefaceAuto = false` and `card.preface = target`, and *deliberately* does not set `card.prefaceLock` — with a comment (`scripts/_workspace_ops.js:164-168`) justifying the omission on the grounds that setting it "would make the connector render something the app does not." That reasoning is backwards. The app's dedup treats `prefaceAuto === false` as the lock (`src/app.js:12934,12941`); the Node renderer treats `prefaceLock` as the lock (`scripts/_recipe_stack.js:482-490`) and `prefaceLock` appears **zero times** in `app.js`. So after any `set_variant`, the connector re-dedups and overrides the preface the edit just derived, while the app keeps it.

Verifiers reproduced this repeatedly against the repo's own loader: `sacred_steel` → app renders "two-stepping voice", connector renders "evangelizing voice"; `jump_blues` after a saxophone edit → "evangelizing voice…" vs "moaning voice…"; `new_wave` → "two-stepping" vs "cajoling". One scan found 33 of 200 sampled `set_variant` edits rendering differently in **all four formats**; another found 21 of 300 traditions diverging after a single edit against a 300/300-identical baseline. The card *state* matches on both sides — only the rendered string differs, which is precisely why `check_edit_parity.js` (state comparison, `:126-160`) cannot see it and `check_app_parity.js` (fresh seeds only, `:62-70`) never reaches it. `check_edit_parity.js:55-57` explicitly excludes `prefaceLock` from comparison as "a difference that is not one" — the exact field that decides render output.

`AGENTS.md:68-70` promises byte-identical renders for the same workspace, registered as `connector-render-parity` in `scripts/_promises.js:131-135`. The MCP server instructions tell the model to present the final recipe string *verbatim* and describe the connector as "identical to what a human sees in the app." Both are false on any edited workspace, and `set_variant` is the connector's most common edit — the handshake mandates seed-then-edit.

The panel split productively here. The minimalist read the cluster as proof that the renderer fork (H7 below) is the root cause and wanted one PR to `@inline` ~1,200 lines and delete four highs at once. The toolmaker, perf, and maintainer seats all independently checked the seam and refuted that: the divergent function is `assignDedupedPrefaces` (`_recipe_stack.js:471-500`), an explicitly-labeled *port* built from different helpers, **not** part of the byte-duplicated compressor block — so `@inline`-ing the compressors deletes zero of these highs. The maintainer's formulation won: *"the real fix is semantic and small."*

**Fix:** unify the lock predicate — one field, one meaning, in both renderers (making `_recipe_stack.js` key on `prefaceAuto` matches the app and needs no state migration). Then add render-after-edit cases to `check_edit_parity.js` so the gate's scope finally matches the promise's scope. Do not attempt the deduplication refactor first: with no gate rendering post-edit state, a unifying PR lands green whether it fixes or inverts the bug.

### H2 · Recipe corruption: environment chunks swallow instrument chunks (F001)

`compressProseRecipe` Phase B (`src/app.js:2585-2624`) groups chunks by their trailing kebab token *across kinds*. If any member of a merged group is an environment chunk, the merged chunk inherits `kind: 'env'` (`:2612`) — and Phase 2's budget trim drops env chunks wholesale (`:2663-2667`). `compressRichRecipe` mirrors it exactly (`:13817-13848`, kind flip at `:13845`), and rich is the sidebar preview default (`:14958`).

This is live on shipped data. Importing `forro_brasileiro` alone renders **"prancing electric baião-2-4-with-zabumba-on-beat-1 bass"** — the tuning name spliced into the middle of the instrument's descriptor. With seven traditions imported, the string no longer contains "electric" at all: the electric-bass card still exists in the workspace but has been deleted from the output, with **no `[+N hidden]` elision notice**. A catalog scan found 9+ live collision pairs — the baião tuning against `electric_bass` fires in five shipped traditions; `leslie-cab` amp against `pipe-organ`; the milonga tuning against `electric_bass`; ten seed traditions collide.

No gate catches it because the Node engine mirrors the same logic — byte parity between two identically-wrong implementations is still green. This is the clearest demonstration in the audit that parity gates are not correctness gates.

**Fix:** partition chunks by kind before trailing-token grouping, or keep `kind: 'inst'` whenever any member of a merged group is an instrument. Separately, the silent-drop path should emit the elision notice it emits elsewhere.

### H3 · Unauthenticated denial of service, three ways (F179, F183, F045)

The connector runs as a single Node process on a Render `starter` instance (0.5 vCPU, 512 MB, `render.yaml:15`). `/mcp` has **no rate limiting in code** — the limiter in `chat.js:162,196` covers `/chat` only, and `server_http.js:6` defers to "edge rate-limiting" that `render.yaml` never configures. Three separate unauthenticated paths each take the service down:

- **F179 — unbounded roster.** `start_recipe`'s `traditions` is `z.array(z.string()).min(1)` with no `.max()` (`mcp/schemas.js:142-148`); the `edits` array likewise (`:153`); `_workspace_ops` has no card cap. Measured: seeding all 2,503 tradition ids costs **18,742 ms of synchronous CPU**, 13,432 cards, 8.18 MB of workspace. 500 ids costs 5.3 s. One POST stalls `/health`, every chat user, and every other MCP caller for ~19 s. Trivially loopable.
- **F183 — permanently poisoned cache.** `_baselineCards` (`mcp/engine.js:86`) is a module-global `Map`, never evicted, and `baselineForCard()` stores an entry for **every distinct `card.traditionId`** (`:98`) — including unknown ids, which fall through and store an empty Map. `traditionId` arrives from the unvalidated workspace (`schemas.js:37` is `z.array(z.any())`). Measured: 400k distinct attacker-chosen ids retained ~315 MB after GC; 800k grew RSS from 256 MB to 500 MB and never released. Roughly 40 sub-2 MB requests OOM the box for everyone, and the restart resets the spend counter and the card-id sequence.
- **F045 — the hottest tool is the slowest.** `searchCatalog` measures 430 ms / 466 ms / 949 ms for `mahogany` / `bright` / `warm tape saturated`, and **10 ms** with `variant` excluded from types. The variant loop iterates 323,709 `(instrument, part, variant)` tuples — because `mergeFamilyParts` copies the 655-variant materials table into every string instrument, though only 10,950 variant ids are distinct — and compiles a fresh escaped `RegExp` per row per term inside that loop (`engine.js:418`). The MCP instructions route *every* id resolution through this tool. `mcp/README.md:151` claims millisecond handlers.

The adversary seat's round-3 argument stands: *"a curl loop pins the 0.5-CPU starter box and starves `/health` on the same loop — failed healthcheck, restart, and reset of the spend counter."* No spoofing, no fork, no approval required.

**Fix:** add `.max()` bounds in `schemas.js` (16 traditions is generous against a 1,000-char ceiling; cap `edits` and `workspace.cards` too); only cache known traditions and bound the cache; hoist one RegExp per term out of the row loop and build a lowercased index once at boot; dedupe variants by id. Then put real rate limiting in the process rather than in a comment about the edge.

### H4 · `search_catalog` returns ids that cannot be used (F023, and mediums F167/F168/F170)

The variant loop (`mcp/engine.js:437-441`) pushes one row per `(instrument, part, variant)` occurrence, with **no dedupe** and **no instrument or part carried on the row**. But a variant id is only actionable as a `(card, part, variant)` triple — `set_variant` needs all three. Measured live: `search_catalog('mahogany')` returns 5,354 rows, **9 of the top 10 are the identical bare `{type:'variant', id:'mahogany'}`**, and the top 50 contain 2 distinct ids.

What makes this a high rather than a nit is the contract around it. The connector's own instructions mandate *"resolve every word to an id with `search_catalog` / `search_prefaces` (never guess ids)"*, and `engine.js:449-462` carries a comment documenting a **live Gemini agent burning 60k tokens** on exactly this failure class — then fixes it for chain rows only, attaching the stage so the id becomes usable. Variants, the target of the single most common edit, never got the same treatment. The toolmaker seat escalated it twice: *"the mandated path dead-ends on the core edit op."* The minimalist seconded with the observation that the fix is already written one loop away.

**Fix:** dedupe variant rows by id and attach the owning `(instrument, part)` as `extra`, exactly as the chain rows already do.

### H5 · Two UI operations that are super-linear in workspace size (F002, F047)

**F002 — `buildUpSetData` enumerates all 2^N−1 subsets.** `for (let mask = 1; mask < (1 << N); mask++)` over N = card count (`src/app.js:16940`), with per-token membership checks inside. The only guard is `cards.length >= 4` (`:17120`), and it re-runs on every format-button click (`:17104-17108`). Benchmarked with realistic 68-token sets: N=16 → 114 ms, N=20 → 1.6 s, N=22 → 6.5 s, roughly 4× per two additional cards, so N=28 is minutes. Worse, at N=31 `1 << 31` is negative and at N=32 it is 1, so the loop skips entirely and the modal reports **"No descriptor overlaps to display"** — a confidently false answer. `symphonic` (17 cards) plus `ethio_jazz` (15) reaches the silent-wrong branch exactly; the multi-second freeze range is trivially reachable.

**F047 — tradition search renders every match, synchronously, per keystroke.** The input handler calls `renderTradPicker` directly with no debounce (`:17340-17344`) and no result cap; search mode renders *every* match with full description, ancestor path, a 13-div fingerprint, two inline SVGs, and a roster join (`:18258-18275`), then `wireTreeEvents` attaches ~2 listeners per row. Against the committed `browse.json`: `q='a'` matches all 2,503 (1.71 MB of description text alone), `'gu'` 1,814, `'dr'` 1,719. Typing the first letters of any tradition name parses multi-MB `innerHTML` into tens of thousands of nodes and wires ~5,000 listeners — twice, once per keystroke — in the app's primary discovery flow.

**Fix:** F002 — hash each token's membership mask and iterate only observed patterns (O(tokens × N)), cap the sets shown, and stop using a 32-bit shift. F047 — cap rendered rows at ~50 with an "N more" note (`matchRank` already ranks), debounce ~150 ms, and use one delegated listener on the container.

### H6 · The gate lattice's scope failures (F059, F057, F139, F201)

These are the findings about the verification system itself, and the panel's formalist seat made the case most sharply: *"every confirmed formal failure is a scope failure — a universally quantified promise gated over the subset where it trivially holds."*

- **F059 — parity coverage is a hand-enumerated matrix.** `check_app_parity` = seed × render. `check_edit_parity` = `set_variant` × state only, sampling one alternate of the *first* ≥2-variant part per tradition (`:107-114`), explicitly excluding `prefaceLock`. `equivalence.js` = descriptors and suggestions. Nothing covers render-after-edit, `set_preface`'s cascade, `set_environment`, or multi-tradition headers. Every verified drift in this audit sits in an unfilled cell, and each new operation also needs a bespoke `faults.js` class (39 hand-written surgery blocks). Cost grows multiplicatively with ops × formats × surfaces while every cell is manual.
- **F057 — ~1,200 renderer lines are hand-duplicated** between `app.js` and `_recipe_stack.js` (all four compressors, `_suppressSubsumed`, `_descriptorTier` + `_MATERIAL_SEGMENTS`, `_sortDescriptorsByPriority`, `_collapseSharedSuffixes`) despite a working `@inline` single-source mechanism already used for `_merge.js` and `_card_descriptors.js` (`build_html.js:191-237`). Verified drift exists in the copies: the unguarded `slice(0, ceiling - 16)` appears in both prose truncates while both tags copies carry `Math.max`; Node seeding shares one chain object across a tradition's cards where `app.js:2200-2203` explicitly requires a fresh object per card. Downgraded to medium by a verifier ("no demonstrated divergence"), then re-escalated by two panelists, then contested by three who showed the parity highs live in the *ported* function rather than the duplicated block. It sits at high as a maintenance hazard with real but bounded evidence — the honest reading is that the duplication has not yet caused a shipped divergence, and the port has.
- **F139 / F201 — the comparator tripwire does not trip.** Both `_recipe_stack.js:58-60` and `src/app.js:2774-2776` tell maintainers the byte-identical `_cmp` copies are "kept in step by `check_app_parity.js`". A verifier ran the experiment: regress the connector copy to bare `localeCompare`, and `check_app_parity` passes **2503 × 4, green**, because the parity gates run both sides in the same Node process under one ICU locale, and en-US collation coincides with codepoint order over today's catalog (documented at `CHANGELOG.md:1380`). No CI leg runs any gate under a non-default locale; `tandem.js:363`'s TIEBREAK regex explicitly *accepts* `localeCompare`; ESLint has no rule; `faults.js` has no comparator fault class. The nondeterminism this pin exists to prevent shipped once already, and the guard the comments point at cannot catch its return.

**Fix:** replace the matrix with one property-style differential harness that applies a seeded random edit script through both surfaces and byte-compares the renders — it subsumes most of the 1,107 hand-picked cells and would have caught F015/F054/F077/F090 mechanically. Add a `da-DK` locale leg (or lint-ban bare `localeCompare`, or both), and correct the two in-source comments that currently assert protection that does not exist.

### H7 · The freshness rebuild is on every PR's critical path (F049)

`ci.yml:8-22` has no `paths` filter, so the `freshness` job (`:137-175`) runs on every push and pull request, rebuilding all 2,503 traditions — ~30 of its ~34 minutes by its own comment, and self-documented linear: 19 min at 1,426 traditions, 30 min at 2,503. Per-tradition profiling puts 95% of the cost in `search(maxIters: 100)` (~370 ms of a 390 ms average); seeding is 5–23 ms and translation 2–8 ms. On 4-vCPU runners `build_static_api.js:52-54` caps workers at `cpus-1 = 3` of the designed 8. A README typo therefore costs ~35 minutes of merge latency, and the catalog grew 76% in a single import — the perf seat extrapolates ~55 minutes at 5,000 traditions with catalog smoke adding ~62 runner-minutes more. The maintainer seat named this *"the single strongest structural deterrent to outside contribution."*

**Fix:** hash the input closure (`references/` + engine scripts); when it is unchanged, reuse the committed `api/` instead of rebuilding. Failing that, path-filter the job for docs-only diffs and move the full byte-compare to the merge queue while PRs run a sampled `--limit` rebuild.

## 4. The themes

**Theme 1 — Wrong quantifiers, not missing tests.** This repo does not lack verification; it has ~9,200 lines of it. What it lacks is scope discipline. `check_app_parity.js:48-53` states the correct standard in its own comment — *"the scope of a parity gate has to be the scope of the promise"* — and the suite violates it: `connector-render-parity` is universally quantified over workspaces and gated over un-edited seeds (F077, F090); "every gate is two-sided" is quantified over all gates and enforced over promise-bound ones (F080); `check_promises` verifies that a marker and a gate reference each other, never that the gate tests the claim (F058); `check_doc_commands` covers a 10-script safelist while the entire `npm run` surface documented in the README goes unvalidated (F150). A gate whose scope is narrower than its claim is not partial protection — it is a false negative generator, because it converts "untested" into "verified."

**Theme 2 — Parity is not correctness.** Three of this audit's most consequential findings (F001, F066/F115 truncation, F116 guard drift) are cases where *both* engines are wrong in the same way, so every byte-parity gate stays green while the shipped output is corrupt. F001 splices a tuning name into an instrument phrase and then silently deletes the instrument; the guard-clause fix for the truncation family propagated to three of six copy-paste sites and the parity gates never noticed because the omission is symmetric. Parity gates answer "do the two implementations agree," which is a useful question but not the product's question. Nothing in the gate lattice asks "is the recipe right" — there is no output-shape assertion, no invariant that every card in the workspace appears in or is explicitly elided from the render, no ceiling assertion on the final string that survives a multi-tradition header.

**Theme 3 — Public, unauthenticated, single-process, unbounded.** The connector's threat model is essentially "nobody will bother." Every input bound that exists is in a comment rather than in `schemas.js`: no `.max()` on rosters (F179), no cap on `workspace.cards` (F184), a `z.any()` workspace whose fields key a permanent module-global cache (F183), rate limiting that covers `/chat` but not `/mcp` (F045, F173), a per-IP limiter keyed on the client-controlled leftmost `X-Forwarded-For` (F041, F173), a spend cap that silently disables itself whenever `GEMINI_MODEL` is not exactly one of two pricing keys (F018, F042) — which is the guaranteed operator response to the inevitable retirement of the pinned `flash-lite` model. The panel correctly de-escalated the *dollar* risk (the key is free-tier, concurrency is 2 and unspoofable), but the *availability* risk is free, unspoofed, and total. Meanwhile this is the only money-spending, credential-bearing surface in the repo and it has **zero automated tests** (F078, F182, F196), deploys on every push to `main` with no CI gate (F079), and its Docker image is never built in CI (F144) — so the first execution of every image is in production.

**Theme 4 — Documentation that is machine-checked for existence, not for truth.** The promise system is a genuinely good idea implemented one level too shallow. Alongside the parity promise being false, two published privacy documents assert the service makes "no outbound network calls" while the same service forwards user chat conversations to Google Gemini (F089, F091) — that is a factual misstatement in a privacy policy and in a connector-directory submission, and it should be corrected before anything else in this section. `server.json`, the published MCP registry manifest, advertises 1,145 traditions and v2.0.0 against a live 2,503 and v2.1.0 (F093), and `check_artifact_fresh.js:66` byte-gates `sitemap`/`llms.txt`/`robots.txt` while excluding `server.json`. `llms.txt` calls the static API a "read-only mirror of the DEFAULT recipe" of the connector when the two "defaults" come from entirely different pipelines — a hill-climb search versus a workspace seed (F056, F094). The README's own quick start dies on a fresh clone because `npm test` needs Playwright browsers and `npx playwright install` exists only in `ci.yml` (F129, F130). And the `LICENSE` is proprietary all-rights-reserved while the machine-checked docs instruct the public to clone and run it (F186).

**Theme 5 — Two growth axes, both unpriced.** The perf seat established with git receipts that traditions and instruments drive *different* costs: tradition imports drive the CI rebuild (F049), the boot payload (F048), and picker search (F047); instrument imports drive the descriptor table that pushes the runtime `<script>` block to 920,764 bytes — **87.8% of the build's own hard 1 MB ceiling** (F112, F161). The "lazy shell" still ships ~2.8 MB compressed / ~11 MB parsed before first render, and 56% of `browse.json`'s 5.0 MB is description and lineage prose that first paint does not need, fetched serially after 6.1 MB of HTML with no preload hint. Nothing in the repo tracks either curve; the ceiling is a hard build failure that will arrive without warning on an instrument import, and the CI curve is already the main contribution deterrent.

**Theme 6 — Data as code, with the seams showing.** 51.8% of `src/app.js` (lines 2894–12637) is a *generated* `DESCRIPTOR_DF` literal committed inside hand-edited source (F111) — the file everyone must open to change the app is mostly machine output, which distorts every line-count intuition, every diff review, and the byte ceiling above. In the catalog itself: 47 traditions across 22 groups compile to byte-identical recipe bodies (F103), at least 4 tradition pairs are the same genre entered twice with contradictory 13-axis vectors (F102), 12 preface pairs of 741 have byte-identical token bundles including three that cross semantic lines (F105), and some environment fields contradict their own rows (Andalusian flamenco palos assigned a Casablanca chaabi studio, F106). The headline counts are real entities, but the tail contains duplicates the dedup policy has not adjudicated.

## 5. Where the experts disagreed

**Is the renderer fork the root cause, or a separate problem?** The **minimalist** opened with the audit's most attractive claim: F015/F054/F077/F090 are one finding, the renderer is hand-forked, the `@inline` mechanism already exists, and *"the best PR here deletes ~1,200 lines and four highs at once."* Three seats independently checked the seam and refuted it. The **toolmaker**: the divergent function is `assignDedupedPrefaces`, explicitly labeled a *port* of the app's function and built from different helpers (`rank`+`byAppRanking` vs `_matchSurvivors`) — it is not in F057's byte-duplicated block list, and the duplicated compressors have never cross-diverged (F116's guard drift replicates *identically* in both mirrors). **Perf** added the mechanical objection: the app's `buildStackParts` calls browser globals while the Node side binds module catalogs and `require()`s the DF, so `@inline` needs hand-written adapters this shape does not fit. The **maintainer** landed the synthesis: the fix is one lock-field alignment plus a gate cell, with `@inline` migration as separate staged PRs later. **Verdict: the refutation is correct on mechanism**, and F057 survives as a real maintenance hazard rather than as the root cause of the parity highs.

**What is the single worst problem?** The **adversary** argued F039 to critical and dismissed the panel's favorite: *"the parity cluster's whole consequence is 'moaning' vs 'evangelizing' in a recipe string — zero attacker leverage, zero dollars, zero outage; it cannot outrank an unauthenticated RCE."* The **formalist** agreed on the ranking but corrected the loot (`GEMINI_API_KEY` is `sync: false`, Render-only, so the prize is the GitHub token) and argued F183 is worse by pure *exploitability* — no fork, no spoof, no approval, just requests. The **toolmaker** held that the parity cluster is the worst *product* defect because it breaks the contract the connector's own instructions mandate. All three are right about different axes; this report ranks by blast radius, which puts F039 first, the DoS trio second, and the parity cluster first among correctness defects.

**Is the gate apparatus ceremony?** The **minimalist** computed 9,188 lines of verification guarding a 4,144-line engine — 2.2× — and called it ceremony substituting for a ~100-line differential harness. The **formalist** and **maintainer** both attacked the denominator as rigged: those gates also guard the 18,803-line app, 67,183 lines of `references/`, the build, and the docs — an honest ratio near 0.1×. The **formalist** then conceded the deeper point while rejecting the framing: a differential harness is the right instrument for equivalence-class promises (F015/F054/F077/F090) but *structurally blind* to unary contract properties like F082, because `app.js` has no `changed`-summary concept to diff against. **Verdict:** the ratio argument fails, the harness argument succeeds for exactly the cluster that motivated it, and both instruments are needed.

**How dangerous is the disabled spend cap?** The **maintainer** twice pushed F042 to high: model retirement is inevitable, the operator's fix (`set GEMINI_MODEL`) silently disarms the only dollar ceiling, behind spoofable per-IP limits, with zero tests and a `/health` that can never notice. The **minimalist** and **adversary** both refuted on arithmetic: `chat.js:38-44` documents the key as free-tier, `:66-69` names Google's per-key quota as the real backstop, and concurrency is fixed at 2 — *"a disarmed $2 cap on a free-tier key buys 429s, not dollars."* **Verdict: medium stands today**, and it becomes high the day billing is enabled — which is worth writing down next to the cap.

**Preload versus restructure.** The **perf** seat claimed splitting prose out of `browse.json` plus one preload hint halves mobile boot. The **minimalist** objected that picker search reads `lineage`+`description` per keystroke (`app.js:18244`), so deferring 56% of the payload means restructuring search, not adding a tag. Unresolved, and correctly so — F047's cap-and-debounce fix would remove that objection, which makes the ordering matter: fix search first, then split the payload.

## 8. Dismissed but instructive

Six findings were refuted outright. Each teaches something about the repo:

- **F120** — "the per-card stack panel opens with a different default format from two entry points." Both initializers genuinely exist (`rich` at `:15813`, `prose` at `:16801`), but nothing in `app.js` or `codex.html` ever emits `data-action="get-stack"`. The second entry point is dead. *Lesson: this codebase has unreachable UI paths that read as live features — the reviewer was right about the code and wrong about the product.*
- **F162** — "extracting the generated literals out of `app.js` is a pure deletion PR." Five call sites hard-depend on the literals living inside `src/app.js`: `build_descriptor_df.js:170` throws, `build_signatures.js:51-56` parses them, tandem checks them, and faults classes #21/#22 perform source surgery on them. *Lesson: the "data inlined into source" problem (F111) is load-bearing infrastructure, not an oversight — the fix is real but staged, not free.*
- **F163 / F164** — two findings about hypothetical breakage after that extraction. *Lesson: verification correctly rejects planning advice dressed as defects.*
- **F174** — "unauthenticated fresh-turn creation is a signature bypass." The HMAC's stated purpose (`chat.js:15-20`) is transcript-forgery prevention and it is enforced on every turn that carries an envelope; starting a fresh turn without one is the intended design. *Lesson: the chat backend's security model is deliberate and documented, even where its input bounds are not.*
- **F192** — "fork PRs can poison the npm cache into the publish job." Cache writes from a fork PR are scoped to `refs/pull/N/merge` and unreadable from `main`. *Lesson: the investigator followed the attack path to its end and reported the negative result — which is exactly what F039 needed and got.*
